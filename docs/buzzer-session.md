# Buzzer session specification (real-use version)

Status: contract for #765〜#769, decided by
[ADR 0010](adr/0010-buzzer-session-model.md) (#763). Nothing here is
implemented yet unless a section says so. The MVP behavior in
[`docs/mvp.md`](mvp.md) remains the running behavior until each stage lands.

Goal (#762): a 5–10 person study session or social event can run a
20-minute quiz without developer help. Questions are read aloud or shown on
existing slides; this app only handles joining, buzzing, judging and scores.

## Responsibilities

| Layer | Owns | Must not |
|---|---|---|
| Room actor (`room.gleam`) | `RoomInstanceId`, `RoundId`, `Revision`, participants, connections, roles, phase, judgments, timers | read JSON, know about sockets |
| Transport (`websocket.gleam`, `protocol.gleam`) | JSON decode/encode, socket lifetime, keepalive (#764), passing tokens to the actor as opaque values | decide permissions, ordering or identity; log tokens |
| Browser (`web.gleam`, `client_js.gleam`) | display, input, keeping its own tokens in `sessionStorage` | decide the winner, use local clocks for ordering |

## Identifiers

| Name | Scope | Generated by | Purpose |
|---|---|---|---|
| `RoomCode` | user-facing | server, at creation (#767) | what people type or scan; today's `RoomId` |
| `RoomInstanceId` | one actor lifetime | actor, at start (random) | tells a recreated room with the same code apart |
| `ParticipantId` | one meeting | actor, at first join (random) | stable identity for buzzes and scores |
| connection generation | one participant | actor, per attach (monotonic) | which socket is current; stale socket events are dropped |
| `ResumeToken` | one participant | actor (≥128-bit random) | proves "I am that participant" on resume |
| `HostToken` | one room instance | actor, at creation | proves host capability; replaced on transfer |
| `RoundId` | one room instance | actor (monotonic int) | one question; round-scoped commands carry it |
| `Revision` | one room instance | actor (monotonic int) | total order of accepted changes |
| `request_id` | one client | client | correlate a reply to a request; not an order |

Tokens appear only in the direct reply to the client that owns them. They
are never part of a broadcast, a snapshot sent to others, a URL, a QR code,
or a log line.

## Roles and permissions

A connection attaches as exactly one role. The host is not a player (does
not buzz); a Display has no `ParticipantId` and is not listed as a
participant.

| Command | Host | Player | Display |
|---|---|---|---|
| `Buzz(round_id)` | ✗ | ✓ (phase `Open`/`Locked`, not excluded) | ✗ |
| `OpenAcceptance(round_id)` | ✓ | ✗ | ✗ |
| `CloseAcceptance(round_id)` | ✓ | ✗ | ✗ |
| `JudgeCorrect(round_id, participant_id)` / `JudgeIncorrect(...)` | ✓ (answerer only) | ✗ | ✗ |
| `NextCandidate(round_id)` / `Reopen(round_id)` | ✓ | ✗ | ✗ |
| `Skip(round_id)` / `NextQuestion(round_id)` | ✓ | ✗ | ✗ |
| `CorrectResult(round_id, participant_id, judgment)` | ✓ | ✗ | ✗ |
| `TransferHost(participant_id)` | ✓ | ✗ | ✗ |
| `EndSession` | ✓ | ✗ | ✗ |
| `Leave` (explicit) | ✓ (ends hosting, see below) | ✓ | ✓ |
| read snapshot / receive events | ✓ | ✓ | ✓ |

Rejected commands get `forbidden` (wrong role), `stale_round` (old
`round_id`), or `invalid_phase`. Hiding buttons in the UI is a convenience
only; the actor checks every command.

The MVP `Reset` command does not exist in v2. Its replacement is the host's
`NextQuestion`.

**Host capability.** Issued once at room creation (#767). The host resumes
with the `HostToken` at any time while the room instance lives; it is not
limited to the participant grace period. `TransferHost` gives the role to a
connected Player: that participant becomes Host (keeps its `ParticipantId`
and recorded score, stops buzzing), receives a new `HostToken`, and the old
token is revoked; the former host becomes a Player with no score. There is no
fallback where someone else becomes host automatically. If the host leaves
explicitly, the phase moves to `Waiting` and the room continues without a
host until someone resumes with the token or the room stops.

## Acceptance phases

```text
            OpenAcceptance                first Buzz
 Waiting ------------------> Open --------------------> Locked
    ^  ^                     |  ^                        |
    |  |    CloseAcceptance  |  |  Reopen /              | JudgeIncorrect
    |  +---------------------+  |  NextCandidate(empty)  v
    |                           +------------------- (answerer excluded)
    |                                                    |
    |  JudgeCorrect / Skip / NextQuestion                | NextCandidate
    +----------------------------------------------------+ (next in queue -> Locked)

 any phase --EndSession--> Finished (terminal, read-only)
```

| Phase | Buzz | Host commands |
|---|---|---|
| `Waiting` | rejected `not_accepting` | `OpenAcceptance`, `NextQuestion`, `CorrectResult`, `TransferHost`, `EndSession` |
| `Open` | accepted, queued; the first one moves to `Locked` and becomes the answerer | `CloseAcceptance`, `Skip`, `NextQuestion`, ... |
| `Locked` | accepted and queued (position assigned), does not change the answerer | `JudgeCorrect`, `JudgeIncorrect`, `Skip`, `NextQuestion`, ... |
| `Finished` | rejected `session_finished` | none except `Leave`; export stays available |

Rules:

- The buzz queue and positions follow mailbox order, as in the MVP. The
  per-question queue cap stays `max_buzzes_per_round = 128` (#691).
- A participant buzzes at most once per question (`already_buzzed`).
- `JudgeCorrect`: answerer +1 point; the question closes (`Waiting`).
- `JudgeIncorrect`: 0 points; the answerer is *excluded* for this question
  and cannot buzz again in it. The host then chooses `NextCandidate` (next
  non-excluded entry in the queue becomes answerer, stays `Locked`; if none,
  back to `Open`) or `Reopen` (clear the queue, keep exclusions, `Open`).
- `Skip`: closes the question with no points.
- `NextQuestion`: increments `RoundId`, clears queue and exclusions,
  `Waiting`.
- `CorrectResult` may change a judgment of any recorded question while the
  session is not `Finished`. A judgment is stored per
  `(RoundId, ParticipantId)`; scores are the sum of current judgments, so a
  repeated correction is idempotent and never double-counts.
- Winner and order are decided by the actor's processing order only. No
  client timestamp or latency compensation is used.

## Revision and stale notifications (#765)

**Implemented** (#765). Wire details are in
[`docs/mvp.md`](mvp.md#suggested-wire-protocol). Until #768 adds roles, the
MVP `reset` stays available to every participant; it now names the round
(`round_id`) and starts the next one, so it already behaves like the later
host-only `NextQuestion` with respect to `RoundId`.

- Every *accepted* state change increments `Revision` by 1. The direct reply
  to the sender and the broadcast to everyone carry the same
  `(room_instance_id, revision)`. A rejected command carries no revision.
- A join/resume reply is a full snapshot with the current revision; the
  actor subscribes the connection in the same message, so the next event the
  client sees is exactly `revision + 1`.
- Client rule: ignore an event whose `room_instance_id` differs from the
  snapshot's (an older room with the same code); ignore `revision <= last`;
  apply `revision == last + 1`; on a gap, request a fresh snapshot (`sync`).
  A duplicate revision is ignored as state but still resolves the pending
  request with the same `request_id`.
- Round-scoped commands carry `round_id`. A mismatch is rejected with
  `stale_round`, so a button pressed on an old screen never affects a new
  question.
- Pending requests on the client are capped and dropped on socket close; the
  server keeps no per-request history.
- Snapshot size is bounded by the limits below, so "event + full snapshot on
  gap" is the default; diff-only resync is not introduced without
  measurements.

## Connections, disconnect and resume (#766)

**Implemented in #766** for Players (wire details in
[`docs/mvp.md`](mvp.md#reconnect)). Host and Display parts below are applied
when those roles exist (#768).

Server side, per participant: `Connected(generation)` or
`Disconnected(generation, since)`.

1. **First join** (Player): client sends `join` with display name. Reply:
   snapshot + `participant_id` + `resume_token`. Client stores the token in
   `sessionStorage` (per tab; a new tab joins as a new person).
2. **Disconnect** (socket closed, heartbeat timeout per #764, or the
   connection process dying): the actor marks the participant
   `Disconnected` and starts `GraceExpired(participant_id, generation)` for
   60 seconds. Buzzes and scores are kept; others see "disconnected".
3. **Resume**: client sends `resume(resume_token)`. If the token matches a
   participant of *this* room instance, the actor bumps the generation,
   attaches the new connection, and replies with a snapshot. Others see
   "reconnected" (no leave/join pair).
4. **Concurrent resume** with the same token: the newest attach wins; the
   older connection receives `session_replaced` and is closed.
5. **Stale socket**: commands, `Leave` or `SessionDown` from a connection
   whose generation is not current are ignored. A `GraceExpired` whose
   generation is not current is ignored.
6. **Grace expired**: the participant is removed from presence. Recorded
   buzzes and judgments stay, attached to the `ParticipantId` and the display
   name snapshot (as today, #30). The token becomes invalid.
7. **Explicit leave**: same as grace expiry, immediately.
8. **Resume failure** reasons, all shown in the UI with a "join as new
   participant" action: `room_gone` (unknown code or different instance,
   e.g. after a server restart), `resume_expired`, `invalid_token`,
   `session_finished`.

As implemented in #766:

- Wire: `resume` carries `v`, `room_id`, `room_instance_id` and
  `resume_token`; the joining `state` carries `resume_token`; participants
  carry `connected`; `participant_disconnected` / `participant_reconnected`
  are revisioned like other changes; `leave` is the explicit leave.
  `session_finished` waits for `EndSession` (#768).
- The browser resumes only when the saved room id **and** display name match
  what it is about to join, so editing the name joins as a new person.
- The "current connection" is the session subject attached by the latest
  join/resume; the generation counter tags grace timers. A participant whose
  connection is replaced is never marked disconnected by the old socket.
- `ParticipantId` is still generated at the connection boundary (random, as
  before); the resume token is generated by the actor. Neither identifies a
  browser across tabs.
- Departed participants are tracked up to 128 per room instance; beyond
  that the oldest departed entries are dropped (their tokens then answer
  `invalid_token`).

Host: steps 2–5 apply with the `HostToken`; step 6 does not apply (the host
role is held until `TransferHost`, explicit leave, or room stop). While the
host is disconnected, the phase is moved to `Waiting` if it was `Open`
(acceptance is not left running without a host); `Locked` stays `Locked`.

Display: no token, no grace. A disconnected display simply re-attaches.

## Room lifetime

- Creation is explicit (#767). With the v2 protocol, joining an unknown code
  returns `room_not_found`; it does not create a room. A reserved room whose
  creator never completes the first attach is stopped after the empty-room
  grace.
- **As of #766:** a room stops when its last participant's grace expires,
  or at once (via `Release`) when no participant is left at all. Until rooms
  can exist without participants (#767) this is the same as the empty-room
  grace below, so no separate timer exists yet.
- The room stops when no connection has been attached for 60 seconds
  (`EmptyRoomGrace(generation)` checked inside the actor; ADR 0006's rule
  with a new trigger). The registry drops the entry on `RoomDown` as today.
- `EndSession` moves to `Finished`; the room then stops by the same
  empty-room rule. Results must be exported before everyone leaves.
- A server restart ends every room. Clients get `room_gone` on resume.

## Limits

| Limit | Value | Notes |
|---|---|---|
| participants (Players, including those within grace) | 64 | existing `max_participants` |
| Displays per room | 8 | new |
| participants tracked per room instance (including departed) | 128 | #766: the oldest departed entries are dropped first, so joining is never blocked; bounds departed players kept for scores |
| questions (`RoundId`) per session | 200 | `NextQuestion` beyond it is rejected `session_full` |
| buzz queue per question | 128 | existing `max_buzzes_per_round` |
| participant grace | 60 s | after the server sees the disconnect (detection itself takes up to 60 s, #764); `room.default_participant_grace_ms` (#766) |
| empty-room grace | 60 s | |
| rooms | `MAX_ROOMS` | rooms in grace count against it |

Values may be tuned in the implementing PR; the PR must update this table.

## Protocol version and migration

- v2 messages carry `"v": 2` in `create`/`join`/`resume`, and every
  snapshot carries `server_version`.
- Since #765: a join without `"v": 2` is rejected with `client_outdated`
  and closed. The v1 protocol is no longer accepted. A v2 client whose embedded version differs
  from `server_version` shows "ページを再読み込みしてください" and stops
  reconnecting. Because the HTML is served by the same server, a reload is
  always enough.
- No dual v1/v2 room state is kept. Planning Poker is not versioned by this
  change.

## Out of scope

Accounts, persistence across restarts, team play, configurable scoring
rules, question authoring, latency compensation, changes to Planning Poker's
identity or permissions (#688 / #694 keep their own constraints), and any
generic session/permission framework.
